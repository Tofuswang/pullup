# CommonGround Business Flow V2

This document reflects the current GitHub code infrastructure, not the original
ideal product spec.

Current code supports two flows inside one Spectrum/iMessage agent:

1. CommonGround member onboarding and demo room recommendation.
2. pullup host event creation, invite approval, sending, and RSVP tracking.

The shared product idea is:

> We do not recommend people. We recommend a room.

## Product Surfaces

### 1. CommonGround Member Surface

Triggered by:

```text
START
```

Purpose:

- onboard a verified user
- collect consent
- collect LinkedIn as a true-person handle
- collect AI Passport
- collect explicit preferences
- generate one demo room recommendation
- collect mutual confirmation
- prepare a local iPhone Calendar-ready event card
- collect vibe feedback

This flow lives in `src/commonground.ts`.

### 2. pullup Host Surface

Triggered by normal host planning messages, for example:

```text
Coffee meetup next Thursday, in-person, 4 people
```

Purpose:

- collect event brief
- draft invite copy
- require host approval
- send approved iMessage invites
- track RSVP status

This flow lives mostly in `src/agent.ts` and uses SQLite persistence.

## CommonGround Member Flow

### Step 1: Private Invitation

User texts:

```text
START
```

System responds with prestige framing:

```text
You are one of a small first circle invited to CommonGround:
a private NTU-origin room network for meeting thoughtful people offline.

We do not do swiping. We design a room worth showing up for.

Reply CONSENT to continue.
```

Business purpose:

- establish scarcity
- position as invite-only
- avoid looking like a generic chatbot
- make the product feel like a private room network

Current implementation:

- `startsCommonGroundFlow()`
- `invitationMessage()`

### Step 2: Consent

User replies:

```text
CONSENT
```

System explains three permissioned inputs:

1. LinkedIn URL for true-person verification only.
2. AI Passport for approved matching signals only.
3. Explicit preferences for logistics, intent, and boundaries.

Business purpose:

- make privacy boundary explicit before data collection
- avoid scraping posture
- keep trust architecture defensible

Current implementation:

- `consentMessage()`

### Step 3: True-Person Verification

System asks user to paste LinkedIn URL.

Allowed input:

```text
https://www.linkedin.com/in/your-profile/
```

Product boundary:

> LinkedIn proves you are real. It does not define your personality or matching
> profile.

Current implementation:

- URL format validation only
- no LinkedIn scraping
- saved in in-memory CommonGround state

Current limitation:

- no external LinkedIn verification API
- no NTU invite-code validation
- no persistent member table yet

### Step 4: AI Passport

System asks the user to paste an app-safe summary generated by their everyday AI.

Requested fields:

- social energy
- conversation style
- interests and taste
- good first-meet settings
- awkwardness triggers
- boundaries

Business purpose:

- get richer signals than dating-app profile fields
- make the user the data controller
- avoid raw chat ingestion

Current implementation:

- accepts long free text
- requires enough text length to avoid empty onboarding
- converts AI Passport + explicit preferences into interpretable research signals
- keeps an embedding-ready text field for future vector retrieval

Current limitation:

- matching is first-pass product heuristic, not a trained embedding recommender yet
- no persistent member profile table yet

### Step 5: Redaction + Approval

System shows a plain-language preview and says:

```text
I will not show this raw text to other users.
Reply APPROVE if this is safe to use, or paste an edited version.
```

Business purpose:

- user can redact before matching
- raw Passport is not exposed in Context Cards
- makes privacy feel real, not decorative

Current implementation:

- if user sends edited text, it replaces Passport summary
- if user replies `APPROVE`, flow moves to preferences

### Step 6: Explicit Preferences

System asks for what should never be inferred:

- intent
- availability
- budget
- neighborhood radius
- alcohol comfort
- preferred group size
- contact-exchange boundary

Example:

```text
open to dating/social, Thu evening or Sun afternoon, NT$800-1500,
Da'an/Xinyi, no alcohol-heavy first meet, group of 4,
contact exchange only after mutual comfort
```

Business purpose:

- separate inferred taste from explicit consent and constraints
- avoid guessing sensitive preferences

Current implementation:

- stored as free text in CommonGround state
- not yet normalized into structured fields

## Research-Style Room Recommendation

After preferences, the system calls the CommonGround recommender module and creates
one demo room:

```text
AI x Career Transition Coffee Room
```

Room includes:

- user + 3 demo people
- activity
- venue style
- why the room works
- first-meeting quality score
- dyadic chemistry score
- group dynamics score
- experience-fit score
- shared context
- warm-up prompts
- boundaries
- methodology notes

Current demo people:

- Mina, AI product manager
- Ethan, NTU alum and fintech builder
- Claire, UX researcher

Business purpose:

- show the core product magic quickly
- demonstrate “room formation,” not profile browsing
- keep the demo deterministic and judge-friendly
- separate person fit, group fit, and activity fit instead of using one vague compatibility score

Current implementation:

- `recommendRoom()`
- `parseResearchProfile()`
- `contextCard()`
- `src/commonground_recommender.test.ts`

Current limitation:

- people are fake seeded users
- no live candidate retrieval from a member database yet
- no trained reciprocal model yet
- no human review queue yet

## Native-App Architecture Boundary

The latest product direction says CommonGround should feel like it lives in
iMessage, but should be architected as a private planning system with an iOS app
as the real assistant brain.

Current repo boundary:

- implemented: Spectrum/iMessage conversational MVP
- implemented: manual local-calendar free-window sharing
- implemented: Apple Maps URL handoff
- implemented: privacy-safe Context Cards and vibe feedback
- implemented: code-level architecture map in `src/commonground_methodology.ts`
- implemented native package: EventKit write-only event creation
- planned native: EventKit full-access conflict detection after explicit upgrade
- planned native: CoreLocation / MapKit travel-time ranking
- planned native: Contacts permission prompt
- planned native: App Intents / Shortcuts
- planned native: web fallback for friends without the app

Product principle:

> The bot can propose and explain. Calendar truth, location truth, and contact
> access must come from explicit user permission or manual fallback.

## Mutual Confirmation

User can reply:

```text
YES
MAYBE
SKIP
```

Rules:

- `YES`: moves to availability collection
- `MAYBE`: keeps the user flexible
- `SKIP`: asks what to tune next time

Business purpose:

- avoid exposing rejection
- make opt-in mutual
- collect negative preference without rating people

Current implementation:

- single-user demo confirmation
- not yet waiting on multiple participants

## Scheduling

After `YES`, system asks user to check local iPhone Calendar:

```text
you: Thu 7:30 PM, Sat 3 PM
Mina: Thu 7:30 PM
Ethan: Thu 7:30 PM
```

System only asks for free windows, not calendar details.

Business purpose:

- avoid Google Calendar OAuth for MVP
- avoid pretending the server can read iPhone Calendar
- keep iPhone as the local source of truth
- support a demo loop where friends can share free windows manually

Current implementation:

- parses simple weekday/time text and friend-labeled windows
- finds overlapping mutual windows when multiple people are provided
- falls back to a user-only hold if only the current user's windows are provided
- asks for `CONFIRM ROOM`
- native `ios/PullupCalendar` package can request EventKit write-only access
  and create the confirmed event on-device

Current limitation:

- no automatic multi-user free/busy API yet
- no full iOS app shell wired to the native package yet

## Event Confirmation

User replies:

```text
CONFIRM ROOM
```

System sends:

- room confirmation
- iPhone Calendar-ready event card
- Apple Maps link
- reminder that feedback is vibe tuning, not person rating

Current implementation:

- `formatIphoneCalendarEventCard()`
- `appleMapsSearchUrl()`
- local iMessage text card, not native calendar write

Product boundary:

> Without a native iOS app, the server cannot silently add events to local
> iPhone Calendar. It can send an event-ready message that the user can add.

## Post-Event Feedback

System asks:

- Did this room feel like your kind of people?
- Did the conversation feel natural?
- Was the activity a good container?
- Was the energy too quiet, balanced, or too intense?
- What should tune next time: people, activity, venue, timing, or group size?
- Anything to privately review for safety or respect reasons?

Business purpose:

- learn vibe preferences
- avoid rating humans as products
- preserve safety escalation path

Current implementation:

- one feedback prompt
- no persisted feedback model yet

## Existing pullup Host Flow

The repo also has a host/event product flow.

Host sends an event idea:

```text

```

The agent collects required Linear-style event fields:

- title
- date
- format
- cost
- audience
- why join
- what attendees learn
- what attendees build or do
- CTA
- venue/location
- capacity
- guest list

Then:

```text

/approve
/send
/status
```

Business purpose:

- this is the operational layer that can eventually help CommonGround Ops
  manage rooms, invites, attendance, and RSVP state
- it already has SQLite persistence and outbound invite queueing

Current implementation:

- `PullupStore`
- `runPullupAgent()`

## V2 Positioning

CommonGround V2 is currently:

> A deterministic iMessage demo for invite-only onboarding, permissioned user
> data collection, and one curated offline room recommendation, built on top of
> the pullup event/RSVP infrastructure.

The next engineering milestone is to turn the seeded demo room into a real
RoomTAIRA recommender pipeline:

```text
Eligibility Gate
→ Candidate Retrieval
→ Reciprocal Matching
→ Group Formation
→ Activity / Venue Recommendation
→ Human Review
→ Context Card
→ Mutual Confirm
→ Scheduling
→ Vibe Feedback
```
